# Toolpack SDK v3.0.0

Date: 2026-08-02

## Highlights

- **Per-instance logger** — `Logger` is now instantiated once per `Toolpack`, each writing to its own log file and config. Running multiple `Toolpack` instances in the same process no longer produces interleaved logs or shared state.
- **Per-instance request counter** — `requestSeq` moved from module-level to instance-level, eliminating sequence number collisions across concurrent instances.
- **`ModeConfig.customTools` and `ModeConfig.toolsConfig`** — custom tools and tool behavior overrides are now scoped per agent via `ModeConfig`, not registered globally at init time. `toolsConfig` values are merged over the global config at request time.
- **Inline `Toolpack.init()` configuration** — `logging`, `hitl`, and `toolsConfig` are now first-class `ToolpackInitConfig` fields. There is no file-based config discovery in the SDK — all settings are explicit code.
- **Agent abort propagation** — `AgentInput` and `AgentRunOptions` now accept `signal?: AbortSignal`. Aborting a root agent cancels the entire delegation chain through `delegate_to_agent` and `delegate_and_forget`.

---

## Breaking changes

| Removed field | Replacement |
|---|---|
| `ToolpackInitConfig.customTools` | `ModeConfig.customTools` (per-agent) or `sdk.loadToolProject()` (global) |
| `ToolpackInitConfig.modeOverrides` | Configure modes via `customModes` / `registerMode()` |
| `ToolpackInitConfig.configPath` | All configuration is now passed inline to `Toolpack.init()` |

## `toolpack-sdk`

### Per-instance `Logger`

`Logger` is now a class. Each `Toolpack` instance creates its own logger configured from the `logging` field in `Toolpack.init()`. Previously a module-level singleton, meaning all instances shared one log file.

```typescript
const tenantA = await Toolpack.init({
  provider: 'anthropic',
  logging: { enabled: true, filePath: './tenant-a.log', level: 'info' },
});

const tenantB = await Toolpack.init({
  provider: 'anthropic',
  logging: { enabled: true, filePath: './tenant-b.log', level: 'debug' },
});
// Each instance writes to its own file independently
```

**`LoggingConfig` fields:**

| Field | Type | Default | Description |
|---|---|---|---|
| `enabled` | boolean | `false` | Enable file logging |
| `filePath` | string | `toolpack-sdk.log` | Log file path (relative to CWD) |
| `level` | string | `info` | `error` \| `warn` \| `info` \| `debug` \| `trace` |
| `console` | boolean | `false` | Mirror output to stdout/stderr |

Environment variables still override programmatic config: `TOOLPACK_SDK_LOG_ENABLED`, `TOOLPACK_SDK_LOG_FILE`, `TOOLPACK_SDK_LOG_LEVEL`, `TOOLPACK_SDK_LOG_CONSOLE`.

---

### `ModeConfig.customTools` and `ModeConfig.toolsConfig`

Custom tools and tool behavior overrides are now attached to a mode rather than registered globally at init time. This keeps tool sets isolated between agents sharing the same `Toolpack` instance.

```typescript
import { createMode } from 'toolpack-sdk';

const analystMode = createMode({
  name: 'analyst',
  systemPrompt: '...',
  customTools: [...myDataTools.tools],   // only available in this mode
  toolsConfig: { maxToolRounds: 20 },    // overrides the global value for this mode
});
```

`toolsConfig` on a mode is merged over the global `toolsConfig` from `Toolpack.init()` at request time — you only need to specify the fields you want to override.

**`ModeConfig` additions:**

| Field | Type | Default | Description |
|---|---|---|---|
| `customTools` | `ToolDefinition[]` | `[]` | Agent-specific tools, never shared across agents |
| `toolsConfig` | `Partial<ToolsConfig>` | `{}` | Per-agent overrides merged over global `toolsConfig` |

---

### Inline `ToolpackInitConfig` configuration

`logging`, `hitl`, and `toolsConfig` are now top-level fields on `ToolpackInitConfig`. The removed fields (`customTools`, `modeOverrides`, `configPath`) relied on implicit conventions; the replacement is explicit configuration.

```typescript
const sdk = await Toolpack.init({
  provider: 'openai',
  tools: true,
  toolsConfig: {
    maxToolRounds: 10,
    additionalConfigurations: { MY_API_KEY: process.env.MY_API_KEY },
  },
  logging: {
    enabled: true,
    filePath: './app.log',
    level: 'debug',
  },
  hitl: {
    enabled: true,
    confirmationMode: 'all',
    bypass: { levels: ['medium'] },
  },
  onToolConfirm: async (tool) => {
    const ok = await promptUser(`Allow ${tool.displayName}?`);
    return ok ? 'allow' : 'deny';
  },
});
```

**`HitlConfig` fields:**

| Field | Type | Default | Description |
|---|---|---|---|
| `enabled` | boolean | `false` | Enable HITL. Auto-enabled when `onToolConfirm` is provided |
| `confirmationMode` | string | `"all"` | `"off"` \| `"high-only"` \| `"all"` |
| `bypass.tools` | string[] | `[]` | Tool names to skip confirmation |
| `bypass.categories` | string[] | `[]` | Categories to skip confirmation |
| `bypass.levels` | string[] | `[]` | Risk levels to skip (`"high"` or `"medium"`) |

---

### Per-instance request counter

`requestSeq` (used to generate unique `requestId` values for logging and tracing) moved from module-level to `Toolpack` instance-level. Multiple instances running concurrently no longer produce overlapping request IDs.

---

### `generate()` abort check at tool-round boundaries

`AIClient.generate()` now checks `request.signal?.aborted` at the start of each tool-call round. If the signal has fired, the loop exits immediately rather than starting another round of tool execution.

## `@toolpack-sdk/agents`

### `AgentInput.signal` and `AgentRunOptions.signal`

Both types now accept an optional `signal?: AbortSignal`. Pass an `AbortController`'s signal to cancel an in-flight agent run.

```typescript
const controller = new AbortController();

const result = await agent.invokeAgent({
  message: 'Do something long-running',
  signal: controller.signal,
});

// Cancel from a stop endpoint, UI button, or timeout:
controller.abort();
```

**Web server pattern:**

```typescript
const activeRuns = new Map<string, AbortController>();

app.post('/api/chat', async (req, res) => {
  const { sessionId, message } = req.body;
  const controller = new AbortController();
  activeRuns.set(sessionId, controller);

  const result = await agent.invokeAgent({ message, signal: controller.signal });
  activeRuns.delete(sessionId);
  res.json(result);
});

app.post('/api/chat/stop', (req, res) => {
  const controller = activeRuns.get(req.body.sessionId);
  if (controller) { controller.abort(); activeRuns.delete(req.body.sessionId); }
  res.json({ ok: true });
});
```

---

### Abort propagation through delegation

`delegate_to_agent` and `delegate_and_forget` now forward the parent agent's abort signal into all sub-agent invocations via `registry.invoke()`. Aborting the root agent stops the entire delegation chain — you do not need to wire the signal manually through each agent.

```typescript
// Aborting executiveAgent also cancels all agents it delegates to
const controller = new AbortController();
await executiveAgent.invokeAgent({ message: '...', signal: controller.signal });
controller.abort();
```

**Limitation:** The signal fires at tool-round boundaries, not mid-execution. A tool call that is already running finishes its current step before the abort is observed. This is standard cooperative-cancellation behavior.
