# @toolpack-sdk/agents v2.7.0

Date: 2026-07-27

## Highlights

- **BaseAgent: concurrent conversation safety** — channel context (conversation ID, triggering channel, trigger flag) is now isolated per async call chain using `AsyncLocalStorage`, eliminating a race condition when two conversations arrive at the same agent simultaneously
- **BaseAgent: per-request mode** — mode is snapshotted per `generate()` call instead of calling `setMode()` on every run, fixing a race when multiple agents share one Toolpack instance
- **Parallel agent spawning** — new `spawn_agents_parallel` tool lets the LLM instantiate multiple helper agents simultaneously
- **AgentMind: concurrent belief deduplication** — shared `_inFlightBeliefs` set prevents duplicate beliefs when two runs produce the same content concurrently
- **Scheduler: job run history** — every execution is recorded; retrieve history with `getHistory(jobId)`

None.

## Bug fixes

### `extractSteps` received incomplete response object

`run()` was passing `{ content, usage }` to `extractSteps()` instead of the full `generate()` response. Any `plan` or `steps` fields on the response were silently dropped, so `AgentResult.steps` was always `undefined` even when the LLM returned structured plan data.

Fixed by passing the full `generated` response object to `extractSteps()`.

## New features

### BaseAgent: concurrent conversation safety via `AsyncLocalStorage`

Previously, channel context fields (`_conversationId`, `_triggeringChannel`, `_isTriggerChannel`) were stored as instance-level properties. When two conversations arrived at the same agent concurrently, the second inbound message could overwrite the first's context mid-execution — `ask()`, `sendTo()`, and `delegateAndWait()` would then operate on the wrong conversation.

These fields are now stored in an `AsyncLocalStorage` context established by `_bindChannel` for each inbound message. Every async operation downstream (including `run()`, `ask()`, `evaluateAnswer()`) reads the context for its own call chain only.

The legacy instance fields remain as a fallback for code that sets them directly (e.g. `agent._conversationId = 'test'` in tests), but they are no longer written by `_bindChannel`.

No API changes. Agents that were already safe (single conversation at a time, or explicit `conversationId` in every `run()` call) are unaffected.

---

### BaseAgent: per-request mode — `setMode()` no longer called in `run()`

`run()` previously called `this.toolpack.setMode(this.mode.name)` before every `generate()` call. Because `setMode()` mutates shared `AIClient.activeMode`, a concurrent run from a different agent sharing the same Toolpack instance could overwrite it, causing tool filtering and system prompt injection to use the wrong mode.

Mode is now passed as a request-level parameter: `generate({ ..., mode: this.mode })`. The AIClient snapshots the mode for the entire request so no subsequent `setMode()` call can affect it.

`setMode()` is still called once in `start()` for backward compatibility with any code that calls `toolpack.getMode()` after starting the agent.

---

### Parallel agent spawning (`spawn_agents_parallel`)

When `spawn` is configured, the LLM now has access to `spawn_agents_parallel` in addition to `spawn_agent`. It accepts an array of `{ template, task }` pairs and runs all spawns concurrently with `Promise.all`:

```typescript
// LLM tool call
{
  "tool": "spawn_agents_parallel",
  "input": {
    "tasks": [
      { "template": "researcher", "task": "Find recent news on HDFC Bank" },
      { "template": "researcher", "task": "Find recent news on Infosys"  }
    ]
  }
}
// → { results: [ { output, spawnedTemplate, depth, metadata }, ... ] }
```

The same depth cap and `allowPromptAddition` semantics as `spawn_agent` apply to each individual task.

---

### BaseAgent: streaming mode

`run()` now checks `mode.streaming` and switches to `toolpack.stream()` when true:

```typescript
const liveMode = createMode({
  name: 'live',
  streaming: true,
});
```

No code change in `invokeAgent` is needed — the switch is transparent. Chunk deltas are concatenated and the final content returned as `AgentResult.output`.

## Improvements

### AgentMind: concurrent belief deduplication

`AgentMind` now maintains a shared `_inFlightBeliefs: Set<string>` across all `DraftBuffer` instances for the same agent. When two concurrent runs produce the same belief text, the second run detects it as in-flight (normalised to lowercase for comparison) and returns `{ action: 'updated_draft', id: 'in-flight-dedup' }` without writing to the store.

The in-flight claim is released on flush — whether the flush succeeds, fails, or is cancelled — so a transient error in one run never permanently blocks subsequent belief writes.

---

### Scheduler: job run history

`SchedulerStore` now maintains a `job_runs` SQLite table. Executions are recorded automatically by the scheduler on completion and failure.

**New type:**

```typescript
interface JobRun {
  id: number;
  jobId: string;
  outcome: 'completed' | 'failed';
  ranAt: number;          // Unix timestamp (ms)
  durationMs?: number;
  error?: string;         // set on failed runs
}
```

**New methods on `SchedulerStore`:**

| Method | Description |
|---|---|
| `markCompleted(id, ranAt?)` | Record a successful execution |
| `markFailed(id, error, ranAt?)` | Record a failed execution with the error message |
| `getHistory(id, limit?)` | Return execution records newest first (default limit: 20) |

```typescript
const runs = store.getHistory('daily-report', 10);
for (const run of runs) {
  console.log(run.outcome, run.durationMs, run.error ?? '');
}
```

The `job_runs` table is created automatically on `SchedulerStore` initialisation via a migration. Existing databases gain the table on first startup without data loss.
